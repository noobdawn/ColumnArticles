# RenderDoc截帧原理

这里简单介绍一下，Renderdoc由三部分组成：

* qrenderdoc.exe
* renderdoccmd.exe
* renderdoc.dll

Renderdoc的工作原理是这样的：

1. qrenderdoc将启动参数封装好传给renderdoccmd
2. renderdoccmd负责启动并挂起目标进程（如果走的是Inject to process则忽略这步）
3. renderdoccmd向目标进程里创建并注入renderdoc.dll
4. renderdoc.dll注入后修改目标进程的导入表，将对图形函数的调用地址指向自身
5. renderdoccmd恢复进程
6. 在实际游戏中，每次调用图形函数进行绘制时，renderdoc.dll作为wrapper将其调用状态进行记录，得到最终的截帧

# 劣化版的ACE如何保护进程

不少游戏的PC版都用的是劣化版的ACE，这种ACE一般没有扫盘，也不会注册驱动，总体来看是一个用户态下的保护软件。

使用RenderDoc截帧由ACE保护的进程的时候一般会弹这个东西：

这里是第一关，即常驻进程扫描，ACE会识别出类似Renderdoc、GPA这类截帧软件是否在运行（包括dll），并判定这是黑客软件，不允许启动游戏，或者终止游戏进程。

第二关则是加壳，观察游戏目录可以发现：

![image-20260731164618645](images\image-20260731164618645.png)

在游戏主程序之外还有一个Base.dll。

最开始我认为是UE自带的，但检查了一下《龙之剑：觉醒》，同样是UE5制作却没有这个东西，可以确定肯定是被人加壳了。

在这种情况下注入的renderdoc.dll会找不到函数的真实调用地址，然后会出现明明已经注入，但游戏窗口左上角就一直没出现RenderDoc的注入提示。

这一情况的根本原因是壳自己接管或者说“废弃”了IAT的功能，导致原RenderDoc通过IAT污染劫持的方法行不通了，具体看下文。

# 如何魔改RenderDoc

## 修改静态特征

首先就是修改静态特征，这个就比较简单，只需要将代码里所有“RenderDoc”/“renderdoc”/“RDC”/“rdc”都换成另一个命名即可。

我自己当然是直接改名为“NoobDawn”/“noobdawn”/“NBD”/“nbd”。

修改之后再编译启动，这时候你会发现ACE会对qnoobdawn进程的存在置若罔闻，至此我们可以开始下一步。

## 注入

以我很早以前浅薄的黑客知识——譬如在……呃……2008或者2009年看《黑客X档案》或者《非安全》之类的杂书——也大概知道，把DLL用 `CreateRemoteThread` 注入到目标进程里是一个很危险（从安全角度看）的事情。

不确定ACE会不会拦截和封号的前提下，注入行为自然是越隐蔽越好，毕竟这涉及我真金白银买的《白银之城》的内测号，而且我对国内二游厂商……嘻嘻，我可不想最后落到“噫，可以（庭外）和解吗”的地步。

这里换成用 `SetThreadContext` 进行注入：

1. 先在目标进程内申请一块内存，写入一段汇编指令，这段汇编指令的作用就是 `LoadLibraryW("noobdawn.dll")` ，然后将标志位置1，开始自旋；
2. 找到游戏内的一个线程，暂停并备份其CPU现场；
3. 把这个线程的指令指针指向我们的汇编指令，将noobdawn.dll载入；
4. 干完活后，标记位置1；
5. 注入器轮询该标记位，发现完工之后，再次暂停线程，把指令指针掰回去，恢复其现场。

接下来详细介绍其各步操作：

### 准备stub代码

注入器先在目标进程里申请一块可读写可执行（RWX）的内存，然后用 `WriteProcessMemory` 一次性写入一个"包裹"：

```plain
remoteMem ──► ┌──────────────────────┐
              │ stub 代码 (45 字节)   │ ← 让借来的线程执行的小程序
              ├──────────────────────┤
              │ 完成标志 (1 字节)     │ ← 干完活置 1，注入器轮询它
              ├──────────────────────┤
              │ 对齐填充 (7 字节)     │
              ├──────────────────────┤
              │ 参数数据              │ ← 比如 "C:\...\noobdawn.dll" 这个字符串
              └──────────────────────┘
```

### stub代码内容

stub代码本质是由8条汇编指令组成的小代码：

```asm
48 83 E4 F0    and rsp, -16
48 83 EC 20    sub rsp, 0x20
48 B9 <8字节>  mov rcx, paramAddr
48 B8 <8字节>  mov rax, func
FF D0          call rax
48 B8 <8字节>  mov rax, flagAddr
C6 00 01       mov byte [rax], 1
EB FE          jmp $
```

从上到下分别是：

1. 用 `and rsp -16` 清零低4位，-16 的补码是 …11110000，对齐栈指针到16字节；
2. 在栈上腾出32字节空间，因为win64约定，调用任何函数前需要白送被调用方32字节的栈空间，这里要调用 `LoadLibraryW` ，当然需要自备；
3. 把参数块地址放进RCX寄存器，参数块里就存着noobdawn.dll的路径字符串；
4. 把 `LoadLibraryW` 的地址放入RAX寄存器然后再call，因为win64的 `call` 指令需要的是相对偏移，所以此处先将64位绝对地址塞进RAX，再做间接调用；
5. 给标记位置1，表示工作完成；
6. jump回自己，无限回旋，等待外界的注入器收拾现场；

### 注入器编排

讲道理看起来还是蛮像……早些年写Delphi的时候遇到的东西的：

1. 首先自然是枚举线程，然后打开线程拿到句柄；
2. 然后有进程句柄就开始申请存放stub代码的内存；
3. 把stub代码及其参数结构都写进去；
4. 找一个线程暂停，并记住其挂起计数器；
5. 获取线程的CONTEXT，作为后续恢复现场使用；
6. 修改线程的指令指针，指向我们前面申请的stub代码地址；
7. 恢复线程运行
8. 轮询标记位，确认是否完成任务
9. 再次暂停线程
10. 将原始的CONTEXT恢复
11. 恢复其挂起计数器

## EAT Hook

### 导入表和导出表

首先说一下ACE加的壳干了什么，不过再说这个之前，又要简单介绍下导入表和导出表。

只需要知道，exe在链接的时候会在exe的PE头内写下一张导入表：既记录了它依赖哪些函数（只有名字，没有地址），也预留了一排等着填地址的格子——这排格子就是 IAT。例如：

> 需要 d3d11.dll 里名叫 D3D11CreateDevice 的函数

这里只有函数名，没有实际的函数地址，这很合理：谁也不知道玩家的机器上 d3d11.dll 会被加载到内存的哪个犄角旮旯。

那么实际的地址怎么来呢？这就得靠dll也公布自家提供了什么函数，这就是导出表（EAT）。同样在PE头记录，写入了自己提供哪些函数、这些函数的相对偏移是多少。

在启动时，Windows加载器登场，它会先翻找exe的导入表，确定对函数的需求；

然后把对应的dll装进内存，翻找其EAT，得到相对偏移，基址加上相对偏移，就得到了函数的真实地址；

最后将这个真实地址填回exe导入表后的格子中，即导入地址表（IAT），后续exe代码每次 `call` 的时候，就可以通过IAT快速找到并直抵真实的函数地址。

原RenderDoc的修改方法正是劫持IAT，把IAT中关于图形API的函数地址指向我们的wrapper，这样游戏一调用 `D3D11CreateDevice` 函数创建设备，真实的图形设备便能落到我们手中，之后整个绘制过程便可任由我们揉圆搓扁。

我们用代理对象把图形设备层层包裹之后，每次游戏调用 `DrawIndexed` 进行绘制，我们便可得到具体的绘制数据。

### ACE加壳逻辑

OK，说了这么久终于说到ACE加壳了，它把Game.exe的导入表抹了，就剩下GameBase.dll的一个无名函数；Game.exe真实的依赖藏在了被加密后的延迟导入区中。

猜测其启动流程是这样的

1. exe启动
2. 调用Base.dll中的无名函数，进入壳运行时
3. 壳运行时用其解密器和私有的导入解析器去获得延迟导入区中的真实依赖，并逐个解析这些dll的函数地址
4. 将这些函数地址回填给exe的各个调入点

所以正常exe调用一个来自dll的函数，会先去IAT中查到函数地址，再call；而加壳之后，exe的调用点会直接得到函数地址，不会去查IAT。

原RenderDoc来到IAT一看就发现，exe说自己根本没有 `D3D11CreateDevice` 函数——

> ”我徒弟（指需要调用的函数清单）呢？“
> ”我不造啊！（指被ACE抹了）“
> “团长（ACE）我跟你没完，你等着我——”

OK，那为了解决这个问题，方法就是我们也不在IAT下手，而是在EAT下手。

### 污染EAT

注入之后，我们立刻去找加载的d3d11.dll，找到它的EAT，EAT在内存的布局大概是这样的：

```plain
导出目录 (IMAGE_EXPORT_DIRECTORY)
   ├── AddressOfNames ──────► 名字表:    ["CreateDXGIFactory1", "D3D11CreateDevice", "D3D11CreateDeviceAndSwapChain", ...]
   │                                     下标:             0                1                     2
   ├── AddressOfNameOrdinals► 序号表:    [       5         ,                 2       ,             3                , ...]
   │                                     
   └── AddressOfFunctions ──► 地址表:    [RVA?, RVA?, RVA 0x12345, RVA?, RVA?, RVA 0xABCDE, ...]
                                   下标:   0     1        2         3     4      5
（最终路径：names[i] 的函数地址在 functions[ordinals[i]]）
```

举个获得函数真实调用地址的例子：

1. 在名字表里线性找 "D3D11CreateDevice"，得到下标为1
2. 取序号 ordinals[1] = 2
3. 槽位 slot = &functions[2]，里面存着 RVA 0x12345
4. 函数调用的真实地址 = d3d11.dll基址 + 0x12345

那么接下来我们有四步要做，第一步就是找到槽位，这个毋庸置疑，根据上面的逻辑，按字符串拿就是了。

接下来是跳过转发导出函数。部分导出函数比如 kernel32 导出的 `HeapAlloc`，它的 EAT 槽位里存的不是函数地址，而是一个字符串 `"NTDLL.RtlAllocateHeap"`，也就是这里不归我管，你找正主去。这种转发类的导出函数污染了也没用，跳过。

接下来就是比较蛋疼的一步，需要分配跳转stub——是的没错，不是直接把wrapper的函数地址替换掉原函数地址，而是继续制作跳转stub函数：

```c++
#if ENABLED(RDOC_X64)
    // mov rax, hookFunc ; jmp rax
    stub[0] = 0x48;
    stub[1] = 0xB8;
    memcpy(stub + 2, &hookFunc, 8);
    stub[10] = 0xFF;
    stub[11] = 0xE0;
    hookset.eatStubUsed += 16;
#else
    // mov eax, hookFunc ; jmp eax
    stub[0] = 0xB8;
    memcpy(stub + 1, &hookFunc, 4);
    stub[5] = 0xFF;
    stub[6] = 0xE0;
    hookset.eatStubUsed += 8;
#endif
```

也就是把钩子函数先推到RAX寄存器，然后jump过去执行。

为什么需要多此一举呢？

答案是 EAT 槽位的物理限制：**它是 32 位 DWORD，存的是 RVA（相对本模块基址的偏移）**，也就是只能表达"模块基址 + 0 ~ 4GB"范围内的地址。而 wrapper 在 noobdawn.dll 里，它可能被加载到 64 位地址空间的任何地方，有可能超过4GB，所以我们需要先拆成两段进行跳转。

第一段跳转，从d3d11.dll跳转到stub；第二段跳转，从stub跳转到wrapper，执行钩子函数。

| 内存位置 | EAT 槽位          | stub                                          | wrapper             |
| -------- | ----------------- | --------------------------------------------- | ------------------- |
| 记录内容 | D3D11CreateDevice | mov rax, <wrapper的64位绝对地址><br />jmp rax | RenderDoc的拦截函数 |
| 注意事项 |                   | 需保证stub在模块基址上的4GB内                 |                     |

这里又引出第二个问题，怎么保证stub的地址是从模块基址可达的？

一种很"民工"但可靠的做法，就是真的去尝试申请：

```cpp
for(addr = 模块基址+1MB; addr < 基址+0xFFF00000; addr += 64KB)
  VirtualAlloc(指定 addr, 一页, RWX);   // 占不到就试下一个坑
```

从模块上方 1MB 开始，每 64KB 试一次"指定地址分配"，直到成功。上限为 `0xFFF00000`，约为4GB，不过还是需要留出余量。

stub就位之后，最后一步就是改写槽位。

EAT默认是只读内存，需要先用 `VirtualProtect` 解锁，把槽位里的相对基址偏移（RVA）改成stub的RVA，再缩回去。同时也记录下来（槽位地址、原RVA、stub RVA），然后在截帧结束卸载的时候恢复回去。

同时改的时候也需要进行检查，因为ACE有可能会检查EAT，可能会恢复我们的修改。这里就没有多少技巧上的空间了，纯粹做拉锯战……每次遍历模块的时候都需要检查一下槽位里的RVA是不是stub的RVA，不是的话就再改一次。这里也就是纯纯的苦力活。

### 抢先加载

在看完壳的逻辑之后，可能会有一个疑问：

> 假设在noobdawn.dll注入、钩子就位之前，壳运行时已经遍历完EAT了，把函数真实地址全部填入了调用点了怎么办？

所以，这就是时间的重要性。

时不我待，我们必须抢跑：

```cpp
for(const char *dll : {"d3d9.dll","d3d11.dll","d3d12.dll","dxgi.dll","opengl32.dll","vulkan-1.dll"})
  if(GetModuleHandleA(dll) == NULL)
    LoadLibraryA(dll);      // 没加载？我现在就替你加载
```

我们抢先一步把相关图形api所需的DLL全部加载进来，立刻挂上EAT Hook，保证EAT源头被污染。后续无论壳运行时走什么路径解析延迟导入区的数据，由于其源头已经指向我们的stub地址，它也拿我们没办法。

## 注入传播

到这里的时候基本上就完成了绕过ACE的部分，不过我在测《异环》的时候发现有点问题。

注入到NTEGame.exe之后，始终未能传播到子进程HTGame.exe中，令人费解。我一度怀疑是不是他妈的中间倒了几手，但打开process explorer看了下HTGame.exe的父进程就是NTEGame.exe。

后续发现，沟槽的放着Window API `CreateProcessW` 不用，跑去用更底层的API。整理一下大概是这样的：

```plain
CreateProcessA / CreateProcessW            kernel32.dll   ← 最常用的入口
        │
        ▼
CreateProcessInternalW                     kernelbase.dll ← 所有变体的汇聚点
        │
        ▼
NtCreateUserProcess                        ntdll.dll      ← 用户态最后一站
        │
        ▼
syscall 指令 ──► 内核 (NtCreateUserProcess 真身)
```

所以，修改后对这三层API都挂上钩子，同时还需要保证不重复挂接，否则会触发重复注入。
